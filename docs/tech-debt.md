# Технический долг

## 🔥 Приоритетные задачи

### 1. Очистить fallback на статичный ROUTE_SCHEDULE
- **Проблема:** Fallback на `CONFIG.ROUTE_SCHEDULE` остаётся в Car/PathBuilder/UI как аварийный сценарий. При появлении настоящих динамических задач важно не допускать рассинхронизации и подготовить безопасный способ загрузки шаблона.
- **План:**
  1. Вынести шаблон дня в `ScheduleManager` (метод вроде `loadTemplate(...)`) и перестать обращаться к `CONFIG.ROUTE_SCHEDULE` напрямую из сущностей.
  2. Добавить в `ScheduleManager` валидацию пустого расписания и сообщать UI о необходимости fallback через единый API.
  3. После вычищения fallback удалить `CONFIG.ROUTE_SCHEDULE` либо оставить его только как сериализуемую заготовку внутри `scheduleTemplates/`.

### 2. Проверка TimeManager при паузе и высоких множителях
- **Проблема:** при длительном простое на паузе `lastTimeUpdate` залипает → резкий скачок времени после возобновления; ручные стабы `Date.now` в тестах дублируются.
- **План:**
  - [x] Сбрасывать `lastTimeUpdate` при выходе с паузы/смене множителя.
  - [x] Покрыть поведение быстрым smoke‑тестом (x1/x5 + пауза).
  - [ ] Вынести тестовый helper для стабилизации `Date.now`, чтобы не дублировать логику в менеджерах.
  - [ ] Подумать о внедрении `timeSource` в конструктор TimeManager для unit‑тестов без monkeypatch.

### 3. Минимальные smoke‑тесты для ключевых менеджеров
- **Проблема:** изменения в TimeManager/ScheduleManager легко ломают симуляцию, но автоматических проверок нет.
- **План:** добавить простые скрипты/юнит‑тесты (например, через `vitest`) для:
  - [x] корректного перехода расписания на новый день,
  - [x] граничных сценариев stay timer после полуночи,
  - [ ] стабильности маршрутов при перепланировании.
